# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Godot 4.7 C++ GDExtension (`opencv_aruco`) that statically links OpenCV (via Conan) to detect ArUco markers and compute their 6DoF poses, plus a Godot test project that renders a mesh on each detected marker. The main deployment target is a Meta Quest 3 (Android arm64, OpenXR passthrough AR); Windows desktop is the development platform.

## Build commands

There is no test suite or linter. Verification = build the extension, run the Godot project (desktop) or export + sideload the APK (Quest).

```powershell
# Windows native (DLL -> project/bin/windows/)
scons                                   # defaults to platform=windows target=template_debug

# Android arm64 for Quest 3 (.so -> project/bin/android/)
$env:CONAN_HOME = "C:\c"                # space-free Conan cache — REQUIRED on this machine
$env:ANDROID_HOME = "C:\asdk"           # junction to the real Android SDK — REQUIRED on this machine
scons platform=android arch=arm64 target=template_debug
```

- This machine's user path contains a space (`C:\Users\Paul Geiger`), which breaks Autotools deps and godot-cpp archiving — hence the two env vars above (README section 5b.4). Keep `ANDROID_HOME` consistent between builds; switching between junction and real path forces a full rebuild.
- First build compiles OpenCV from source through Conan (~10–20 min); later builds hit the Conan cache. Per-target Conan output lives in `conan_install/<platform>.<arch>.<target>/`; delete that folder or touch `conanfile.py` to force a dependency re-resolve.
- `SConstruct` bootstraps Conan itself (pip install + `conan profile detect`) — no manual Conan setup needed. For Android it uses the checked-in Jinja profile `profiles/android-arm64` (NDK path derived from `ANDROID_HOME`); `CONAN_HOST_PROFILE` overrides it.
- APK export happens in the Godot editor on Windows (Project > Export, preset "Meta Quest 3"). The editor does NOT build the Android `.so` — it must already exist in `project/bin/android/` before exporting. Sideload: `adb install -r <path>.apk`; stop the app: `adb shell am force-stop de.unigreifswald.opencvaruco`.

## Naming invariant

The library name `opencv_aruco` and entry symbol `opencv_aruco_library_init` must stay consistent across three places: `SConstruct` (`libname`), `project/bin/opencv_aruco.gdextension`, and `src/register_types.cpp`. godot-cpp composes filenames as `<lib?><name>.<platform>.<target>[.double].<arch><suffix>` — note `.double` comes BEFORE the arch, and Windows DLLs have no `lib` prefix while Linux/Android `.so`s do (the Android SCons branch forces `SHLIBPREFIX="lib"` because Windows hosts default to no prefix).

## Architecture

Data flows: camera frame (GodotAndroidCamera plugin on Quest, CameraServer on desktop) → GDScript worker thread → C++ OpenCV detection → camera-space marker poses → baked to world space using the head pose at the frame's capture time.

**C++ side (`src/`)** — `OpenCVProcessor` (a `Node`) exposes three detection entry points; the one that matters is **`detect_markers(image, head_pose, corners_out)`**, which takes a frame the caller already owns (avoids a second capture) plus the head pose at that frame's capture time — the only per-frame input, since only the caller can know it. It runs ArucoNano's `ArucoDetector` (vendored header-only `src/aruco_nano.h`, DICT_ARUCO_MIP_36h12) + `solvePnP` and returns a Dictionary of marker id → `Transform3D` in **world space**: `head_pose * lens_pose` is pre-multiplied onto every result, so the caller has nothing left to apply (identity `head_pose` yields near-camera space — OpenCV→Godot basis change = 180° X-flip baked in). `corners_out` is a debug-only out-parameter (Godot Dictionaries are shared references): it receives id → the 4 detected pixel corners, divided back out of the downscaled detection frame into the original frame's pixel space, filled before the solve loop so it shows what the detector saw rather than what survived `solvePnP` — for the TCP overlay.

Everything else it needs is an **inspector property of the node** (`camera_intrinsics`, `camera_distortion`, `image_downscale_factor`, `lens_rotation_raw`, `lens_translation`, `aruco_patch_size`, `aruco_patch_sizes`) rather than a call argument — that is what collapsed a 7-argument call to 2, and it keeps invariants that used to span the language boundary inside one class: the intrinsics are scaled by the *clamped* downscale factor at the point the frame is resized, and the distortion `cv::Mat` is built in its setter instead of being rebuilt from a `PackedFloat64Array` every frame. The setters rebuild the derived values immediately, so an edit in the **remote inspector of a running deploy takes effect on the next frame** — notably true of the lens pose, which used to be derived once in GDScript's `_ready` and could not be tuned live at all. `get_marker_size(id)` is the single id → side-length resolution (table entry when present and positive, `aruco_patch_size` otherwise) and is bound so the GDScript scales the rendered box with the exact number `solvePnP` used; `get_lens_pose()` exposes the decoded transform for the hand-eye capture. Note that `Vector4`/`Quaternion`/`Vector3` components are `real_t` = float32, so the intrinsics and the lens rotation hold ~7 significant digits regardless of the inspector's step — well under the calibration's own noise, but it is why the inspector will not show every digit in the source. Every property carries an explicit `PROPERTY_HINT_RANGE` step for exactly one reason: without a hint the inspector snaps to 0.001, and editing a distortion coefficient there rounds both tangential terms to zero. On Android it also reads the Quest passthrough camera intrinsics via the NDK Camera2 API — the Quest's world-facing passthrough cameras are ids "50"/"51". That dump, and everything else that prints, lives in `initialize()` rather than the constructor: the class is now a node **authored in the scene**, so `PackedScene` constructs it before it applies a single property and long before any `_ready`, leaving no way to set the debug-print static early enough. GDScript calls `set_debug_prints_enabled()` and then `initialize()` on consecutive lines of `_ready`; the constructor is silent and builds only the detector. `initialize()` is idempotent and returns immediately under `is_editor_hint()`, since opening the scene in the editor constructs the node too.

`OpenXRHeadLocator` (also a `Node`, `src/OpenXRHeadLocator.{h,cpp}`) is the second registered class: it returns the head pose at an **arbitrary** `XrTime` via `xrLocateSpace`, which for a time in the past is the runtime's *measured* estimate rather than the prediction the pose history holds. It creates its own `XR_REFERENCE_SPACE_TYPE_VIEW` space (Godot exposes the play space but not its internal view space) and locates it against `OpenXRAPIExtension.get_play_space()`; `locate_head(xr_time)` returns `{valid, tracked, transform, flags, result}`, with `transform` in **play space** — the caller reapplies `XROrigin3D`, `XRServer.get_reference_frame()` and the world scale (`_play_space_to_world`). The `XrPosef` → `Transform3D` conversion is done **by hand** (7 floats; OpenXR and Godot share the right-handed Y-up convention) and must stay that way: `OpenXRAPIExtension.transform_from_pose()` takes a `const void *` that godot-cpp does not marshal through, and measured on device it returns **identity for every pose**, silently and with no error — which reads as a plausible-but-wrong pose sitting head-height from the real one and never changing with time. Nothing links the OpenXR loader: Godot already owns the instance and session, so the three entry points come from `get_instance_proc_addr` and `src/openxr_minimal.h` hand-declares only the structs/enums they need (vendoring the real SDK header would mean a new include path for both platforms or a cross-compiled Conan dep, for three structs). The VIEW space is a child of the XR session, so it is released on `OpenXRInterface.session_stopping` — the destructor is too late, the session is usually gone by scene teardown.

**Scene layout (`project/aruco_markers.tscn`)** — the root is an **unscripted `XROrigin3D`**; its children are `XRCamera3D` (→ `OpenXRMetaEnvironmentDepth`), `XRStartup` (a plain `Node` carrying `xr_startup.gd`), `OpenCVProcessor` (the extension class, carrying `open_cv_processor.gd`), `Patches`, `CameraLayer` → `CameraPreview`, and `DirectionalLight3D`. So the app script does **not** sit on the root: it lives on the `OpenCVProcessor` node and reaches its siblings through `..` paths (`xr_origin` is `$".."`). Two consequences worth remembering. `class_name ArucoMarkerSource` is therefore **not** a `Node3D` — nothing ever used its own transform, but consumers get a plain `Node`. And with `reloadable = false`, the app's main script hangs off a node whose type comes from the DLL: if the extension fails to load, **saving the scene in that state drops the node along with its script assignment and every exported override**, so never save a scene that opened with errors.

**GDScript side (`project/open_cv_processor.gd`)** — patch nodes are created and freed at runtime, never authored in the scene: the first detection of a marker id spawns an `aruco_patch<id>` `Node3D` (one shared `BoxMesh`, scaled to that id's real marker size) under the `Patches` container (its own node so the runtime churn does not interleave with the authored siblings in the remote scene tree; it sits at identity and poses are assigned as `global_transform`, so it is numerically free), and an id absent from detection results for `PATCH_LOST_TIMEOUT_MS` (500 ms — a grace period, since detection drops markers for the odd frame) gets freed. The `marker_nodes` dictionary is the id → node registry and the thing that keeps ids unique: `_get_or_create_patch` returns the existing node for a known id, so no id can gain a second node or inherit another's. Both creation and pruning happen in `_apply_detection_result` on the main thread. Detection (~40 ms on Quest: ~20 ms `detectMarkers` since the ArucoNano swap, down from ~60 ms with OpenCV's, plus `solvePnP`) runs as one-shot `WorkerThreadPool` tasks (at most one in flight, results collected via `is_task_completed` polling) with a single pending-frame slot (newest frame wins); `get_image()` and all scene-tree writes stay on the main thread. Marker poses are baked to world space with the head pose at the frame's capture time (timestamped pose history, interpolated; sampled at frame arrival and passed into `detect_markers` as its second argument, which combines it with the lens pose C++-side; capture time = the plugin's sensor timestamp on Quest, now − `CAMERA_LATENCY_MS` on desktop) — pairing old pixels with the live head pose makes patches "swim". On the Quest each history entry is stamped with the time its pose *describes* — xrWaitFrame's predicted display time (`OpenXRAPIExtension.get_predicted_display_time()`) — rather than with "now", because OpenXR hands out poses predicted for the upcoming display: measured on device that lead is 40–80 ms, shrinks as the render rate rises and sawtooths ~40 ms peak-to-peak within that (pdt steps in whole 13.89 ms display quanta while the wall clock runs on), so no single constant could cancel it. `POSE_LOOKUP_TRIM_MS` (default 0, was `POSE_LOOKUP_BIAS_MS` at 35–50 ms before the stamping) is left only for a constant residual: start-vs-middle of exposure. (It also used to cover a suspected one-frame stagger between the pdt and the pose read beside it — the locate check below **measured that away**: locating the head at `get_predicted_display_time()` reproduces `XRCamera3D` to 0.02–0.3 mm, often bit-for-bit, while one display period is worth ~7 mm at normal head speed. So Godot's head pose belongs to pdt, not `get_next_frame_time()`, and the stamping carries no stagger.) The once-a-second `openxr pdt sync` line is the health check for it — the stamping is only valid while pdt advances exactly once per `_process`, i.e. `ratio` ≈ 1.00 with `dupes=0`. **`use_xr_locate_space`** (`@export`, default **on**) switches the whole lookup to `OpenXRHeadLocator` instead: the frame's sensor timestamp is mapped to `XrTime` (identity on the Quest passthrough feed, where both clocks are CLOCK_MONOTONIC) and handed to `xrLocateSpace`, so the pose is **measured rather than predicted** and the history + interpolation are bypassed entirely; a frame the runtime will not answer falls back to `_head_pose_at`, counted as `locate_fallbacks` on the flow trace. Even perfectly stamped, history entries are forecasts for a display time 40–80 ms out, so the predictor's error rode into every marker pose — worst during exactly the fast head motion where it shows. The once-a-second `openxr locate check` lines are the gate, and they passed on the Quest: **(A)** probes both `get_predicted_display_time()` and `get_next_frame_time()` against the live `XRCamera3D` (pdt won, see above), **(B)** probes `pdt − 60 ms` and got valid + tracked poses 1–31 mm away from the live one, i.e. this runtime really serves measured history rather than clamping to the newest pose. Both need head *motion* to mean anything — standing still zeroes every number. The `openxr locate raw` line beside them prints the play-space pose before any conversion, which is what distinguishes "wrong pose" from "no pose at all". Consumers (avatar rigs, gizmos) address markers by **id**, never by patch node, since the nodes are transient: `class_name ArucoMarkerSource` exposes `get_marker_pose`/`has_marker`/`marker_age_ms`/`markers_fresh`/`markers_ever_seen`/`get_average_marker_pose`/`get_marker_node` plus a `markers_updated` signal, and `_marker_poses`/`_marker_last_seen` deliberately outlive the patch nodes so a consumer keeps its last good pose and its age through a dropout (bounded at 250 entries by the dictionary). `_sync_marker_sizes` runs at the start of every detection task and now only pushes sizes onto the live patch meshes (via `get_marker_size`); the id → size table it used to mirror for the C++ side is gone, since the detection resolves ids against its own properties. Its old "only while no task is in flight" caller contract went with that table. `xr_startup.gd` (on the `XRStartup` node) switches on Meta passthrough (alpha blend + transparent viewport) and the XR viewport — it does **not** initialise OpenXR: `xr/openxr/enabled=true` in `project.godot` means the engine does that before the main scene loads, which is why `_setup_xr_locator`'s `is_initialized()` check does not depend on node order. A TCP frame-streamer (`tools/tcp_receiver.py`, port 7007 via `adb reverse`) exists for debugging: it sends the frame plus **two** overlays and a trailer as one packet — the detection's pixel corners (drawn green), the same markers *reprojected* (red), and the baseline angle — and the receiver draws both with `cv2.aruco.drawDetectedMarkers`, so what you see is what the **device** produced rather than a second opinion from a laptop-side detection. That is why the send sits in `_poll_detection_task` (the frame held in `_stream_img`) and not at frame arrival — the corners do not exist until the worker is done — and why it runs *before* the pending frame is handed on, which would overwrite `_stream_img`. Frame, both marker blocks and the trailer go into the one `_tcp_out` buffer: it drains asynchronously with `put_partial_data`, so anything written to the socket directly would overtake the pixels still queued in front of it, and a dropped frame has to drop its markers with it (the receiver reads a fixed byte count per frame, so a half-sent set desyncs every frame after it — which also means sender and receiver must be updated together).

The **red overlay is the lens-pose test**, and it exists because the green one cannot be. Green shows only the ArUco corner extraction: `corners_out` is filled *before* the solve loop and never touches `camera_intrinsics` or `camera_distortion`, so a perfect green fit proves the detector is good and says nothing whatever about the intrinsics or the lens pose. Red is `project_marker_corners(world_poses, head_pose)` (C++, beside the detection so it uses the same `Kamera_matrix`, `distort_mat` and `lens_pose`, and the **native-frame** intrinsics — unscaled by `image_downscale_factor`, since green was already divided back into original-frame pixels): it inverts `head_pose * lens_pose`, undoes the OpenCV→Godot basis change (`F = diag(1,-1,-1)`, its own inverse — the sign pattern looks transposed against the forward path because that builds the `Basis` from *columns* while godot-cpp indexes *rows*), and runs `cv::projectPoints`. It must be fed poses from a DIFFERENT frame: reprojecting a frame's own poses with its own head pose cancels algebraically (`(H·L)⁻¹ · H·L·M = M`) and would draw a perfect square however wrong the lens pose is. So `_stream_detected_frame` latches the world poses for `REPROJ_BASELINE_MS` (5000 ms — long enough to cover the same displacement slowly *and* quickly inside one hold, which is what separates a geometry error, scaling with how far the head moved, from a timing error, scaling with how fast) and reprojects *those*. The baseline length is the whole sensitivity of the test: the gap goes as `fx · head_turn · lens_error / range`, so with `fx = 435` and a marker at 0.65 m a 5 mm lens error over the ~80 ms between two detections is **0.3 px** (invisible) while the same error over a second of head turning (~50°) is ~3 px (visible). A longer baseline costs nothing when the calibration is right — a correct world pose is head-independent, so red stays on green however old the reference is; it only bounds how long the marker must stay continuously in view. **The head has to move and the marker must not**: standing still drives the gap to zero regardless of the calibration, which is why *two* baselines ride along in the trailer — head turn in degrees and head displacement in metres — and the receiver prints both first and refuses to interpret a gap until one of them has grown. Which one grew is the diagnosis, and they are not interchangeable. **Turning** exposes `lens_translation`; **strafing cannot**, because with the head orientation fixed the relative motion `A` is a pure translation and `L⁻¹AL = [I | R_Lᵀ·Δ]`, in which `t_L` has cancelled out entirely. What strafing exposes instead is anything that puts the marker at the wrong *depth* — `aruco_patch_sizes` or the focal length — since parallax against a wrongly-placed point grows with viewpoint change, at `fx · (Δ/range) · |1 − 1/k|` for a scale error `k` (0.5% at 0.5 m and 0.65 m ≈ 1.7 px, i.e. right at the visibility threshold). `lens_rotation_raw` shows up under both. So a sawtooth that appears when strafing but not when turning is a scale problem, not a lens-pose one, and reaching for another hand-eye run would be chasing the wrong parameter. The value of all this over judging the rendered mesh through the headset is that it lands in **camera pixels**, with passthrough reprojection onto the depth proxy and the eye projection out of the loop — the two stages that make the naked-eye comparison ambiguous. What it measures is `lens_pose` *and* the capture-time head-pose lookup jointly; a timing error scales with head *velocity* while a lens error scales with head *displacement*, so slow-but-wide head motion isolates the lens pose.

**Camera backends** — Android/Quest uses the `GodotAndroidCamera` Android plugin (`project/addons/GodotAndroidCamera`, a CameraX AAR): frames arrive as raw Y-plane bytes on the CPU (no GPU→CPU readback) together with the **sensor timestamp** of each frame, which is mapped onto Godot's clock to look up the head pose at the true capture time. The offset is calibrated against the clock the feed actually stamps on: boottime (`get_clock_offset_nanos`) for `timestamp_source: "realtime"`, CLOCK_MONOTONIC (`get_monotonic_clock_offset_nanos`) for `"unknown"` — the Quest passthrough feeds report "unknown", and the boottime offset would be silently wrong by the headset's doze time since boot. XrTime (the predicted display time the pose history is stamped with, above) is CLOCK_MONOTONIC on the Quest and therefore gets its own bridge, `_xr_clock_offset_ns`; both are resampled together in `_resample_clock_offsets` so they cannot drift apart — the lookup compares a camera timestamp mapped with one against a history entry mapped with the other, so an error common to both cancels while a divergence becomes a silent bias (on the passthrough feeds they hold the same number). If the plugin singleton is missing from the APK, the script falls back to Godot's native CameraServer (4.5+) with the fixed `CAMERA_LATENCY_MS` guess. Windows desktop needs the `CameraServerExtension` addon, instantiated via `ClassDB.instantiate()` with an untyped var so the script still parses on Android where that class doesn't exist. Rebuilding the AAR: `./gradlew build` in `../godot-android-camera`, then copy `plugin/demo/addons/GodotAndroidCamera` over `project/addons/GodotAndroidCamera`.

**Export guard (`project/addons/aruco_export_guard`)** — an `EditorExportPlugin` that fails the Android export if a required `.so` is missing for an enabled ABI. Without it Godot packages a 0-byte `.so` and reports success. It also deletes the broken APK in `_export_end()`. Keep its `ABI_ARCHS` map in sync with the `.gdextension` file.

## Platform gotchas (hard-won, do not regress)

- **Quest rendering must be Vulkan**: `rendering_method="mobile"` in `project.godot`. The GL renderer crashes on the first frame with "Failed to import swapchain IPC textures".
- **Android API level is pinned to 24** in `SConstruct` (godot-cpp defaults to 21) because OpenCV's videoio needs `libcamera2ndk`/`libmediandk`, which only exist in the NDK sysroot from API 24+. The Android branch also explicitly links `camera2ndk mediandk android log`.
- **C++ exceptions are enabled** (`disable_exceptions=False`) — OpenCV headers require them; godot-cpp disables them by default.
- **Windows CRT matching**: Conan's `compiler.runtime` is derived from godot-cpp's `use_static_cpp` (→ `/MT`). Never link `*d.lib` debug variants of third-party libs — godot-cpp's `template_debug` still uses the release CRT.
- **Quest hand-tracking**: a "controllers required" dialog on launch means the APK lacks the hand-tracking feature — enable Meta Hand Tracking (Optional) in the export preset.
- **Camera feed selection**: Quest exposes feed "1 | FRONT" plus the passthrough pair "50 | BACK"/"51 | BACK"; pick a "BACK" feed, and `CameraServer.monitoring_feeds = true` plus `feed.set_format(...)` must happen before `set_active(true)` or no frames arrive.
- NDK version `23.2.8568313` is pinned by godot-cpp; the Conan profile's `compiler.version=12` matches its clang. OpenXR Vendors plugin v5 lives in `project/addons/godotopenxrvendors`.

Comments in `SConstruct`, `conanfile.py`, and parts of the C++ are in German; that's the existing style, keep edits consistent with the file you're in.
